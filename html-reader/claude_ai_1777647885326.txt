🌍 What is Crowdfunding Really?
Crowdfunding is basically "many people funding one idea together". Instead of one investor giving $100,000, you get 1,000 people each giving $100.
Think of it like this — your friend wants to open a restaurant but has no money. Instead of going to a bank, he posts online: "Help me open my restaurant, I need $50,000". Then strangers, friends, and fans all chip in small amounts. That's crowdfunding.
👥 Who is Involved?
1. 🧑‍💼 Creator (Campaign Owner)
The person or company who needs money. They create a campaign explaining their idea, set a goal, and a deadline.
Example: A Bangladeshi startup wants to build a solar-powered rickshaw. They need ৳500,000 to build the prototype.
2. 🙋 Backer (Supporter / Funder)
Regular people who give money to support the idea. Could be anyone — strangers, fans, family.
3. 🏢 Platform (Your App!)
The middleman website that connects creators and backers. It handles payments, listings, and takes a small commission fee (usually 3-5%) from successful campaigns.
This is what you are building!
4. 💳 Payment Gateway
The service that processes the money. In your case — SSLCommerz. It moves money from the backer's bank/card to the platform safely.
💸 Now About "Donation" — You're Right to Question This!
In crowdfunding, money given is not always a pure donation. It depends on the type of crowdfunding:
Type 1: 🎁 Reward-Based Crowdfunding
Backer gives money → Gets a reward/product in return.
This is NOT a donation. It's more like pre-ordering.
Example: "Give $50, get our product when it launches"
Platforms: Kickstarter, Indiegogo
Type 2: ❤️ Donation-Based Crowdfunding
Backer gives money → Gets nothing in return. Pure giving.
This IS a real donation.
Example: "Help us rebuild after the flood"
Platforms: GoFundMe
Type 3: 📈 Equity-Based Crowdfunding
Backer gives money → Gets a small ownership stake in the company.
Like investing in a startup.
Example: "Give $1,000, own 0.1% of our company"
Type 4: 💰 Lending-Based Crowdfunding
Backer gives money → Gets it back with interest later.
Like a loan from the crowd.

Creators raising money for flexible goals

Higher risk for backers ⚠️ (no refund if goal fails)

💡 Key Design Decisions Explained
Why is fundingModel always keep-it-all for charity?
Because charity campaigns keep whatever is raised — every penny helps flood victims regardless of the goal.
Why is totalRaised and backerCount stored in campaign?
So you don't have to count all donations every time someone visits the campaign page. These get updated with every new donation — much faster to query.
Why is rewardTiers a separate collection?
Because one campaign can have many reward tiers. Embedding them inside campaign would make the document too large and hard to query individually.
Why is charityDetails null for reward campaigns?
Because reward campaigns don't need organization details. Keeping it null keeps the schema consistent across both types.

totalRaised = ৳200,000

Important — Net Amount Calculation:
totalRaised should only count
status: "charged" donations
NOT:
❌ pledged (not yet charged)
❌ failed (payment failed)
❌ refunded (money returned)
❌ cancelled (AON failed)

javascript
const totalRaised = await Donation.aggregate([
{
$match: {
campaignId: campaign._id,
status: "charged"
}
},
{
$group: {
_id: null,
total: { $sum: "$amount" }
}
}
])
const platformFee = totalRaised * 0.05
const netAmount = totalRaised - platformFee

💡 Key Design Decisions Explained
Why store transactionProof?
Admin uploads a screenshot or PDF receipt after manually sending money. Creator can verify the transfer happened. Builds trust.
Why store platformFeePercent AND platformFeeAmount?
Because your fee percentage might change in the future. If you only store the percent, you can't know what fee was applied at the time of withdrawal. Storing both gives a permanent record.
Why one withdrawal per campaign?
A creator can only withdraw once per campaign — after it fully succeeds. No partial withdrawals. Keeps accounting simple and clean.
Why rejectionReason stored in DB?
Creator deserves to know WHY their withdrawal was rejected. Also creates an audit trail for admin accountability.

🧠 What Does a Notification Need to Store?
Who receives it?
userId → the person who sees it
What type is it?
A type string so frontend knows what icon/color to show
The message
Short readable text
e.g. "Someone just backed your EcoBottle campaign!"
Reference data
Link to the relevant document
So clicking the notification takes user somewhere useful
e.g. campaign page, withdrawal page etc.
Is it read?
isRead boolean

🔄 How Notifications Are Created
Every important action in your backend triggers notification creation:
javascript
// Example — when donation succeeds
async function onDonationSuccess(donation, campaign, user) {
// 1. Update donation status in DB
await Donation.updateOne(...)
// 2. Update campaign totalRaised in DB
await Campaign.updateOne(...)
// 3. Create in-app notification for backer
await Notification.create({
userId: donation.backerId,
type: "donation_successful",
title: "Donation Successful!",
message: `You successfully backed ${campaign.title} with $${donation.amount}`,
reference: {
campaignId: campaign._id,
donationId: donation._id,
campaignTitle: campaign.title,
campaignThumbnail: campaign.thumbnail
},
isRead: false
})
// 4. Create in-app notification for creator
await Notification.create({
userId: campaign.creatorId,
type: "new_backer",
title: "New Backer! 🎉",
message: `${user.name} just backed your ${campaign.title} with $${donation.amount}!`,
reference: {
campaignId: campaign._id,
donationId: donation._id,
campaignTitle: campaign.title,
backerName: user.name,
amount: donation.amount
},
isRead: false
})
// 5. Send email notifications
await sendEmail(user.email, "donation_successful", {...})
await sendEmail(creator.email, "new_backer", {...})
}
🔗 How Notifications Connect to Other Collections
notifications.userId        → users._id
notifications.campaignId    → campaigns._id
notifications.donationId    → donations._id
notifications.withdrawalId  → withdrawals._id
💡 Key Design Decisions Explained
Why store campaignTitle and campaignThumbnail inside reference?
So when you display the notification you don't need to do an extra DB query to get the campaign name and image. The notification is self contained and fast to render.
Why isRead boolean and not a readAt timestamp?
For notifications, you only need to know read or unread — not exactly when it was read. Keeps it simple.
Why no updatedAt field?
Notifications are never edited. Once created they are permanent. Only isRead changes via a separate update call.
Why store backerName and amount inside reference for creator notifications?
Creator sees "John Smith backed $50" directly in the notification without extra queries. Fast and clean.
